The Ultimate Rulebook

Technical Architecture, Mathematical Formulas, and Core Logic of the Attendance Processor

1. System Architecture

The Attendance Processor is a hyper-optimized desktop application designed for maximum performance, offline capability, and complete architectural transparency. It completely bypasses heavy server frameworks in favor of a native execution model.

1.1 The Stack

  • Frontend (UI): A Single-Page Application (SPA) written in raw HTML, JavaScript, and Tailwind CSS. It runs natively using PyWebView. As of V8, the entire CSS compiler is embedded locally, making the app 100% offline-capable on all firewalled or air-gapped computers.
  • Backend (Python API): Python handles heavy file parsing (Excel), PDF generation (ReportLab), and SQLite interactions.
  • Bridge: Python exposes an API object directly to the JavaScript window (window.pywebview.api). Zero HTTP overhead is required.
  • Database: An embedded SQLite database running in Write-Ahead Log (WAL) mode for high concurrency and speed. Data is saved in a data/attendance.db file located next to the application executable.

2. The Parser Engine

The system digests complex biometric Excel exports (specifically the Secureye ONtime format) and normalizes them into strict database records.

2.1 Date and Header Heuristics

The parser dynamically seeks rows starting with Emp Code to identify column headers. Because ONtime spreads days horizontally (e.g., columns for 1, 2, 3...31) and repeats these headers across page breaks, the parser mathematically tracks month boundaries. If an imported report spans July 25 to August 10, the parser dynamically calculates when day '1' shifts to August to guarantee zero data loss.

2.2 The Absolute Presence Rule (V9)

To eliminate ambiguity, the parser enforces a strict Boolean assignment for attendance status. The logic is hardcoded as follows:

if punch_in or punch_out:
    status = "PRESENT"
else:
    status = "ABSENT"

Rule: If an employee possesses any biometric punch (either arrival or departure), they are mathematically defined as PRESENT. Missing hours are dealt with later by the financial engine, not by denying their presence.

2.3 The 12:00 PM Single-Punch Heuristic

If the biometric machine only registers a single punch for a day, the system must guess if the employee forgot to punch in or forgot to punch out. The system uses a strict 12:00 PM (Noon) threshold:

  • Punch < 12:00 PM ➜ Assumed as Punch In (Punch Out is NULL).
  • Punch ≥ 12:00 PM ➜ Assumed as Punch Out (Punch In is NULL).

3. The Financial & Salary Engine

The mathematical heart of the application is the Salary Report macro (def_salary). This engine computes minute-by-minute wage calculations while dynamically handling employee-specific schedules.

3.1 Custom Schedules vs Global Defaults

Each employee is evaluated against their specific scheduled shift. If an employee has a custom_arrival or custom_departure set in the Staff Directory, the engine uses it. Otherwise, it falls back to the Global Check-in/out times. This defines the employee's Shift Minutes for the day.

3.2 Valid Worked Minutes Calculation

The engine prevents employees from artificially inflating their salary by arriving too early or staying too late. The formula caps their payable time at their scheduled shift boundaries:

Effective In = MAX(Actual Punch In, Scheduled Arrival)
Effective Out = MIN(Actual Punch Out, Scheduled Departure)
Valid Minutes = Effective Out - Effective In

3.3 The 50% Single-Punch Penalty Rule

If an employee has only punched in, OR only punched out, calculating the difference between the two punches is impossible. To handle this fairly, the engine mathematically grants the employee exactly 50% of their scheduled shift minutes for that day.

The Code Logic:
The engine computes the scheduled shift duration in seconds, and divides it by 120 (which is mathematically identical to dividing the shift minutes by 2).

3.4 The 1-Day Paid Leave Credit Rule

The Salary engine has a built-in forgiveness protocol. If an employee is ABSENT for one or more days in the month (excluding global holidays), the system automatically grants them a Leave Credit multiplier of 1.

The engine then takes their standard daily Shift Minutes and adds it to their total Payable Mins. This effectively means every employee gets exactly 1 paid day off per month. If they are absent 3 times, they are only docked pay for 2 of them.

3.5 Final Salary Formula

The exact payout is determined by creating a hyper-accurate Per-Minute Rate:

Per-Minute Rate = Monthly Base Salary / (Shift Minutes × Working Days in Month)
Earned Salary = Payable Mins × Per-Minute Rate

This guarantees mathematical perfection down to the specific minute, removing all subjective approximations.

4. The Query & Conflict Engine

The application allows users to build dynamic SQL queries using the visual interface. It seamlessly translates UI blocks (Fields, Operators, Joiners) into parameterized SQLite queries.

4.1 The Dual-Mode Conflict Resolver

A common error in standard SQL is mixing GROUP BY clauses with non-aggregated columns. If a user asks to group by "Employee Name" but also requests "Punch In Time", SQLite will simply return a random row's punch time. This is dangerous.

The application intercepts this using the detect_group_conflict algorithm. If it detects a conflict, it safely splits the request into two entirely separate database calls:

  1. Summary (Grouped) Table: Executes the aggregation perfectly.
  2. Detail Table: Strips the GROUP BY and returns all underlying raw rows that match the filters.

Both tables are presented simultaneously on the screen.

5. Modifying Global Data

5.1 Calendar Holidays

When a day is clicked in the Calendar Settings, it is injected into the calendar_days database table. The salary engine automatically subtracts the count of these days from the total days in the month to compute the true Working Days divisor.

5.2 The Query Log

Every SQL query (including automated macros and custom filters) is logged to the query_log table. The system automatically prunes this table to keep only the last 100 queries, preventing database bloat while providing total transparency into the engine's mathematical execution.
